# AI Assistant Context for iRacing Safety Car Generator

Patterns, conventions, extension points, and gotchas. For module-level reference, see `.ai-modules.md`.

## Quick Reference

- **Language:** Python 3.13
- **Architecture:** Event-driven threading with state machine pattern
- **GUI Framework:** Tkinter
- **Testing:** pytest with pytest-mock for SDK mocking
- **Platform:** Windows-only (pywinauto for window automation), but supports cross-platform development via mock implementations
- **Key Dependencies:** pyirsdk (iRacing SDK), pywinauto (Windows automation), codetiming (performance monitoring)

## Architecture Overview

Python 3.13 desktop app: Tkinter GUI + iRacing SDK integration. Two threads: main thread runs the GUI (`App`), a worker thread runs the `Generator` detection loop at ~1 Hz.

**Data flow:** `Generator._loop()` → `Drivers.update()` (fetches SDK telemetry with double-buffering for delta detection) → `Detector.detect()` (runs enabled sub-detectors) → `ThresholdChecker.register_detection_result()` → `ThresholdChecker.threshold_met()` → if met, `Generator._start_safety_car()` sends chat commands to iRacing.

**Detection system** uses composite/protocol pattern: `Detector` holds a list of `SupportsDetect` implementations (RandomDetector, StoppedDetector, OffTrackDetector). Each returns `DetectionResult` which feeds into `ThresholdChecker`'s sliding time window with per-driver event tracking, proximity clustering, and dynamic race-start multipliers.

**Safety car procedures** after deployment: pace laps → wave arounds (3 strategies via factory) → optional class split via `!eol` commands.

**Cross-thread coordination:** The generator thread never calls Tkinter. It posts `StateChanged` / `ClassSplitConfirmationRequested` events to `Generator.ui_events` (a `queue.Queue`), which `App._process_generator_events()` drains on the main thread every 100 ms. The UI talks back through `Generator.stop()`, `throw_manual_safety_car()`, `skip_wait_for_green()` and `confirm_class_split()`, which only set `threading.Event`s. See pattern 6.

**Settings** persist via `ConfigParser` in `src/settings.ini`, wrapped by typed property accessors in `src/core/settings.py`.

## Critical Patterns to Follow

### 1. State Machine Pattern (GeneratorState)

The Generator uses a strict state machine; every transition goes through `Generator._set_state()`:

```python
class GeneratorState(Enum):
    STOPPED = 1
    CONNECTING_TO_IRACING = 2
    CONNECTED = 3
    WAITING_FOR_RACE_SESSION = 5
    WAITING_FOR_GREEN = 6
    MONITORING_FOR_INCIDENTS = 7
    SAFETY_CAR_DEPLOYED = 8
    UNCAUGHT_EXCEPTION = 9
```

**State Transitions:**

- `STOPPED` → `CONNECTING_TO_IRACING` (`run()` called; published before the thread starts)
- `CONNECTING_TO_IRACING` → `CONNECTED` (SDK and iRacing window connected) or `ERROR_CONNECTING`
- `CONNECTED` → `WAITING_FOR_RACE_SESSION` (connection verified)
- `WAITING_FOR_RACE_SESSION` → `WAITING_FOR_GREEN` (race session started)
- `WAITING_FOR_GREEN` → `MONITORING_FOR_INCIDENTS` (green flag shown)
- `MONITORING_FOR_INCIDENTS` ↔ `SAFETY_CAR_DEPLOYED` (threshold met / green flag)
- Any state → `STOPPED` or `UNCAUGHT_EXCEPTION`, published as the very last thing the generator thread does (after shutting down the SDK)

**Publishing state (src/core/generator.py):**

```python
def _set_state(self, state: GeneratorState):
    self._state = state
    self.ui_events.put(StateChanged(state))  # The App applies it on the main thread
```

The App mirrors the state in its own `generator_state` property, whose setter updates the widgets. Only `App._process_generator_events()` (main thread) sets it. The mirror is for display only: it lags up to 100 ms, so decisions (Start vs Stop, manual safety car) use `generator.state`.

**When to modify:** Only add new states if adding fundamentally new operational modes. Always use `_set_state()` in the generator so the UI hears about the transition; add the state's texts to `util/state_utils.py` and, if it means "not running", to `is_stopped_state()`.

### 2. Double-Buffering Pattern (Drivers)

The Drivers class maintains two copies of driver data to enable delta detection:

```python
# src/core/drivers.py:11-18
class Drivers:
    def __init__(self):
        self.current_drivers: list[Driver] = []
        self.previous_drivers: list[Driver] = []

    def update(self, ir):
        self.previous_drivers = self.current_drivers.copy()
        self.current_drivers = self._build_drivers(ir)
```

**Purpose:** Detect stopped cars by comparing `total_distance` between current and previous frames.

**When to modify:** Add new fields to the Driver TypedDict if you need additional driver properties for detection.

### 3. Protocol Pattern (SupportsDetect)

Detectors use structural typing via Protocol for loose coupling:

```python
# src/core/detection/detector_common_types.py:41-49
class SupportsDetect(Protocol):
    def detect(self) -> DetectionResult:
        """Run detection and return results."""
        ...

    def should_run(self, state: DetectorState) -> bool:
        """Check if detector should run based on current state."""
        ...
```

**When to add new detector:**

1. Implement the `SupportsDetect` protocol
2. Add event type to `DetectorEventTypes` enum
3. Update `Detector.build_detector()` to instantiate your detector
4. Add settings to `DetectorSettings` dataclass

### 4. Builder Pattern (Detector)

The composite Detector is constructed via a builder:

```python
# src/core/detection/detector.py
@staticmethod
def build_detector(settings: DetectorSettings, drivers: Drivers):
    """Build the detector with the enabled detectors based on settings."""
    detectors = {}  # keyed by DetectorEventTypes
    if settings.random_detector_enabled:
        detectors[DetectorEventTypes.RANDOM] = RandomDetector(
            chance=settings.random_probability,
            start_minute=settings.random_start_minute,
            end_minute=settings.random_end_minute,
            max_occurrences=settings.random_max_safety_cars
        )
    if settings.stopped_detector_enabled:
        detectors[DetectorEventTypes.STOPPED] = StoppedDetector(drivers)
    # ... OFF_TRACK and MEATBALL the same way ...
    return Detector(detectors)
```

Detectors take `drivers` plus plain constructor arguments; there are no per-detector settings classes.

**When to modify:** Add new detector types to the builder when creating new detection algorithms.

def wave_arounds_factory(wave_around_type: WaveAroundType):

### 6. Threading: UI Events Queue + Signals

Two threads, and only the main thread touches Tkinter:

- **Main thread (App):** Tkinter mainloop. `Generator.run(settings)` only snapshots the settings (`GeneratorSettings`, `DetectorSettings`, `ThresholdCheckerSettings`), clears all signals, publishes `CONNECTING_TO_IRACING` and starts the thread — it never blocks.
- **Generator thread (`Generator._run`):** connects to iRacing (its own `irsdk.IRSDK()` per run), builds `Drivers`/`Detector`/`ThresholdChecker`, runs `_loop()`, then shuts the SDK down and publishes the final state last.

**Generator → UI:** events on `generator.ui_events`, drained by `App._process_generator_events()` via `after()`:

```python
self.ui_events.put(StateChanged(state))                        # every state transition
self.ui_events.put(PreflightWarnings(warnings))                # App shows a warning dialog; the run continues
self.ui_events.put(ClassSplitConfirmationRequested(commands))  # App shows dialog, answers via confirm_class_split()
```

**UI → Generator:** methods that only set `threading.Event`s:

```python
generator.stop()                     # shutdown_event
generator.throw_manual_safety_car()  # throw_manual_sc_event
generator.skip_wait_for_green()      # skip_wait_for_green_event
generator.confirm_class_split(ok)    # confirm_class_split_event
```

**Rules:**

- Never call Tkinter (widgets, `after()`, variables, dialogs) from the generator thread, and never give the generator a reference to the App. Tkinter is only safe on the thread running `mainloop()`; calls from the worker fail with `RuntimeError: main thread is not in main loop` once the window is closed.
- The generator thread reads only its own settings snapshot (`self.settings`), never the App's live `Settings`.
- Closing the window stops the generator, hides the window and destroys it once the thread has finished (`GENERATOR_SHUTDOWN_TIMEOUT_S`). Don't `join()` the thread on the main thread while it could still be waiting on the UI (e.g. a class-split confirmation).

**Dataclasses for configuration (settings snapshots):**

Components never read the live `Settings` (`src/core/settings.py`) at runtime. Each one gets a frozen snapshot, defined in the **same module as the class that uses it**, with defaults and a `@staticmethod from_settings(settings)` factory:

| Snapshot | Defined in | Used by |
| --- | --- | --- |
| `DetectorSettings` | `src/core/detection/detector.py` | `Detector.build_detector()` |
| `ThresholdCheckerSettings` | `src/core/detection/threshold_checker.py` | `ThresholdChecker` |
| `GeneratorSettings` | `src/core/generator.py` | `Generator` (eligibility window, procedures) |

```python
# src/core/generator.py
@dataclass(frozen=True)
class GeneratorSettings:
    detection_start_minute: float = 0.0
    max_safety_cars: int = 2
    # ...

    @staticmethod
    def from_settings(settings):
        return GeneratorSettings(
            detection_start_minute=settings.detection_start_minute,
            max_safety_cars=settings.max_safety_cars,
            # ...
        )
```

`Generator.run()` builds all three once per run (the e2e `DumpReplayer` does the same). Field names may be adapted to the consumer (e.g. `ThresholdCheckerSettings.time_range` ← `event_time_window_seconds`). When a snapshot gains a field, also add its key to `_SETTINGS_DEFAULTS` in `src/core/tests/test_utils.py`.

### Logging

**Per-module loggers:**

```python
import logging
logger = logging.getLogger(__name__)
```

**Log levels:**

- `logger.debug()`: Detailed diagnostic information
- `logger.info()`: General informational messages (state changes, events)
- `logger.warning()`: Unexpected behavior that doesn't stop execution
- `logger.error()`: Errors that affect functionality
- `logger.exception()`: Exceptions with stack traces

**Configuration:** Logging is configured via `src/logging.json` and outputs to `logs/{timestamp}.log`

- The file handler is attached to the **root** logger (level `WARNING`). Entries under `loggers` only set a level and propagate to root — do **not** give them their own `handlers`, or every record is written twice.
- The `core` and `util` entries set `INFO` for everything under those packages, so a new module logs `INFO` and above without any config; add an entry under `loggers` only to get its `DEBUG` records. Third-party libraries stay at the root's `WARNING`.
- The packaged build runs with `--noconsole` (no stderr), so never rely on `print()` or stderr to surface errors.

## Common Gotchas

### iRacing SDK Quirks

**1. Negative lap progress:**
The SDK occasionally returns negative values for `CarIdxLapDistPct`. Always filter these out:

```python
# src/core/detection/stopped_detector.py:47-48
if driver["lap_distance"] < 0:
    continue  # Skip this driver
```

**2. Entire field appears stopped (lag detection):**
If the SDK lags, all cars may show as stopped. Detect and ignore this:

```python
# src/core/detection/stopped_detector.py
# If length of stopped cars is entire field, clear list (lag fix)
if len(stopped_cars) >= len(self.drivers.current_drivers) - 1:
    logger.warning(f"Entire field appears stopped ({len(stopped_cars)} cars), clearing list (likely lag)")
    stopped_cars = []
```

**3. Pace car in driver list:**
The pace car is included in all driver arrays. Always filter it out:

```python
if driver["is_pace_car"]:
    continue
```

**4. Cars in pits:**
Check both `on_pit_road` and `track_loc` for comprehensive pit detection:

```python
# src/core/detection/stopped_detector.py:51-53
if driver["track_loc"] in [TrkLoc.aproaching_pits, TrkLoc.in_pit_stall] or driver["track_loc"] == TrkLoc.not_in_world:
    continue
```

**5. TrkLoc is not a standard Python Enum:**
`irsdk.TrkLoc` looks like an enum but is a custom class — it is **not iterable** (`for t in TrkLoc` raises `TypeError`). Its values are plain integers:

| Constant                 | Value |
| ------------------------ | ----- |
| `TrkLoc.not_in_world`    | `-1`  |
| `TrkLoc.off_track`       | `0`   |
| `TrkLoc.in_pit_stall`    | `1`   |
| `TrkLoc.aproaching_pits` | `2`   |
| `TrkLoc.on_track`        | `3`   |

Note the **typo** `aproaching_pits` (one 'p') — this is the actual irsdk constant name. In NDJSON dumps, `CarIdxTrackSurface` stores these as raw integers, so comparisons work with either the constant or the int value. When writing tests against dump data, compare with the `TrkLoc` constants.

**6. A driver's place in the drivers list is not its CarIdx:**
`Drivers.current_drivers` only holds the cars listed in `DriverInfo.Drivers`, so CarIdx values can have gaps and the pace car can sit well past the end of the list (e.g. 16 cars at CarIdx 0-15 and the pace car at CarIdx 62). `driver_idx` and `pace_car_idx` are CarIdx values: never use them to index the drivers list or a list built from it. Look drivers up by `driver_idx`, and get positions behind the SC keyed by `driver_idx`:

```python
# src/core/procedures/wave_arounds.py
relative_to_sc = driver_positions_from_safety_car(drivers, pace_car_idx)
drivers_by_idx = {driver["driver_idx"]: driver for driver in drivers}
```

All recorded dumps in `docs/dumps/` have contiguous CarIdx values with the pace car last, so they will not catch this; add a test with gaps (see `test_wave_arounds_non_contiguous_car_idx`).

**7. The per-car arrays are not always 64 entries:**
By default the `CarIdx*` arrays have 64 entries. With `[Misc] irsdkLogAllCars=1` in iRacing's `app.ini` (added in 2026 Season 3 Patch 1) they grow to the size of the entries table (72 seen live), and the pace car can sit at CarIdx 64 (seen in a live 50-car league race). Never assume 64: size lists by the array length or the highest CarIdx. A replay can show a different layout from the live session (the pace car at 62 in a replay of a race where it was at 64), most likely because the arrays follow the viewer's own setting.

**8. No pace car in events without a race session:**
An event with a race session (practice, qualifying and race) lists the pace car in `DriverInfo.Drivers` from its first session on. An event without one, such as a standalone pre-race practice, has no pace car entry at all, while `PaceCarIdx` is still set (62, or -1 with `irsdkLogAllCars=1`; all seen live). The preflight check only checks the pace car when the event has a race session. A `PaceCarIdx` of -1 would silently index the last element of a Python list, so never use it without a pace car entry.

**9. Switching events does not disconnect:**
Moving from a standalone practice event into the race event keeps the SDK connected; `WeekendInfo` (`SessionID`/`SubSessionID`), `SessionInfo.Sessions` and `DriverInfo` simply change. Never cache the session list or driver list across loop iterations. (Known issue: `Generator._wait_for_green_flag()` reads the session list once, so a generator started in a standalone practice event raises a `KeyError` when the race event loads.)

### Threading Model

**Generator runs in separate thread:**

- Main loop runs at ~1 Hz (1 second sleep + loop execution time)
- Uses `threading.Event` for coordination (shutdown, manual SC, skip wait, class-split confirmation); `run()` clears them all, and the manual SC / skip-wait signals are also cleared whenever monitoring (re)starts, so presses made while waiting don't carry over
- Never touch Tkinter from the generator thread — post an event to `ui_events` instead (see pattern 6)
- A manual safety car is thrown on the next loop iteration while monitoring, regardless of the eligibility window (earliest minute, minimum time between safety cars)
- Code that only runs after the loop has iterated (e.g. `Timer.timers` stats) must handle the loop never running: stopping while waiting for green, or `max_safety_cars = 0`

### State Management

**In the generator, always use `_set_state()`:**

```python
# Good - publishes a StateChanged event for the UI
self._set_state(GeneratorState.MONITORING_FOR_INCIDENTS)

# Bad - the UI never hears about it

```

In tests, assert on `generator.state` and read the published transitions from `generator.ui_events`.

### Tkinter UI

**1. Disabled ttk widgets silently ignore `delete()`/`insert()`.**
When a variable has a trace that disables other widgets (e.g. `var_wave_arounds` → `toggle_wave_around_config`), fill those widgets *before* setting the variable. Setting it first left "Laps before wave arounds" empty whenever wave arounds were off, so saving failed and Start did nothing (v0.3.0 – v0.5.1).

**2. Keep comboboxes `readonly`.**
Re-enabling a combobox must use `state="readonly"`, not `"normal"` — `"normal"` makes it free text, and `current()` then returns `-1`.

**3. Every UI setting goes through the `fields` table in `App._save_settings()`.**
When adding a settings widget, add a `(setting, UI label, widget value, parser)` row there. Use `_parse_int`/`_parse_float`/`_parse_selection` so invalid input is reported in the error dialog instead of raising.

**4. Exceptions in Tkinter callbacks are handled by `App.report_callback_exception()`.**
It logs the traceback and shows an error dialog. Don't swallow exceptions in button handlers to "keep the UI alive" — let them reach this handler so they are visible.

**5. Settings are stored without interpolation.**
`Settings` uses `ConfigParser(interpolation=None)`, so `%` is a literal character in `settings.ini`.

## Domain-Specific Logic

### Wave Around Strategies

Three strategies (see `src/core/procedures/wave_arounds.py`):

1. **WAVE_LAPPED_CARS**: Cars 2+ laps down OR 1 lap down and behind class leader
2. **WAVE_AHEAD_OF_CLASS_LEAD**: Cars ahead of class leader in running order but behind overall leader
3. **WAVE_COMBINED**: Union of both strategies

**Execution order:** Commands sent in running order behind safety car (closest to SC first)

- Events expire after `time_range` seconds (default: 5s)
- Per-driver tracking prevents double-counting
- Supports both per-event-type and accumulative (weighted) thresholds
- Dynamic threshold multipliers during race start period

### Detection System Composite

The Detector coordinates multiple detection algorithms:

```python
# src/core/detection/detector.py:52-61
def detect(self) -> BundledDetectedEvents:
    """Run all enabled detectors and bundle results."""
    results: list[DetectionResult] = []

    for detector in self.detectors:
        if detector.should_run(self.detector_state):
            result = detector.detect()
            if result:
                results.append(result)

    return BundledDetectedEvents(results)
```

**Key insight:** Each detector independently decides if it should run based on `DetectorState` (time window, lap range, etc.)

## Extension Points

### Adding a New Detector

`MeatballDetector` is a complete recent example of every step below.

1. Create `src/core/detection/your_detector.py` implementing the `SupportsDetect` protocol; take `drivers` (and plain constructor arguments if it needs configuration, like `RandomDetector`)
2. Add the event type to `DetectorEventTypes` in `detector_common_types.py`
3. Add `Settings` properties in `src/core/settings.py` (`your_detector_enabled`, `your_cars_threshold`, `your_weight`, ...)
4. Add the enabled flag (and any constructor arguments) to `DetectorSettings` and its `from_settings()` in `detector.py`
5. Update `Detector.build_detector()` to add your detector under its event type
6. Add the event type to `ThresholdCheckerSettings` in `threshold_checker.py`: the default `accumulative_weights` / `event_type_threshold` dicts, the `__post_init__` `setdefault`s, and `from_settings()`
7. Add the new setting keys to `_SETTINGS_DEFAULTS` in `src/core/tests/test_utils.py`
8. If users can configure it: add widgets in `App._create_widgets()`, fill them from settings, and add rows to the `fields` table in `App._save_settings()`
9. Create tests in `src/core/detection/tests/test_your_detector.py`
10. If it reads an SDK value nothing else uses, add it to the preflight check (see "Relying on a New SDK Value")

### Adding a New Wave Around Strategy

1. Add enum value to `WaveAroundType` in `wave_arounds.py`
2. Implement function matching signature: `(drivers: list[Driver], pace_car_idx: int) -> list[str]` (`pace_car_idx` is a CarIdx, see SDK quirk 6)
3. Update `wave_arounds_factory()` to return your function
4. Add tests

### Relying on a New SDK Value

Right after connecting, every run calls `run_preflight_checks()` (`src/core/preflight.py`). If the SDK data breaks one of our assumptions, the generator posts `PreflightWarnings` and the App shows a warning dialog; the run continues. This is how we find out when an iRacing update changes the data (like the pace car moving to CarIdx 62). When code starts reading a new SDK value, or relies on a new assumption about one:

1. Add the value to `REQUIRED_TELEMETRY` or `REQUIRED_DRIVER_KEYS`, or add the assumption to one of the `_check_*` functions
2. Add a test to `src/core/tests/test_preflight.py`. `test_recorded_sessions_pass` runs every dump in `docs/dumps/` through the checks, so a check that flags real data fails there

## Testing Requirements

- **New features**: Always include unit tests and integration tests where applicable. Plan for testing as part of the implementation, not as an afterthought.
- **Bug fixes**: Always write a regression test that **fails before** the fix and **passes after** the fix. This proves the bug is reproduced and resolved.
- **E2E tests**: For detection pipeline changes, add scenarios to the e2e test framework in `src/core/tests/test_e2e_detection_and_procedures.py` using real SDK dumps from `docs/dumps/`.
